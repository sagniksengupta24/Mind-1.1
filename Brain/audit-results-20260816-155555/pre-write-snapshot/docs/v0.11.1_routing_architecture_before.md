# Mind1.1 v0.11.1 pre-change routing architecture

Recorded before implementation on 2026-07-30 from commit
`3f71bd56823bbde35e70d9c57dbb858f0d1e8894`.

## Runtime path

`Agent.ask` calls `HierarchicalRouter.route_typed`, converts the result through
the legacy compatibility view, and passes the typed route to
`ToolExposureAuthority`. The authority recomputes visible tools from route,
mode, granted capabilities, lifecycle phase, and inspection/mutation state.
`ToolRegistry` performs the final schema, mode, write, shell, and runtime-state
checks. Model action output is separately constrained by a JSON Schema and
parsed by `action_parser`.

## Current semantic decision

`HierarchicalRouter.interpret` normalizes the request and directly assigns:

- task class and response mode;
- intent type, ambiguity, risk, and required capabilities;
- inspection prerequisites and incident codes.

`HierarchicalRouter._select_route` then assigns specialist, immediate tool
family, preferred/fallback tools, and reason code in the same ordered rule
chain. `_confidence` returns one of a few rule-based values. The router itself
does not call the model, abstain, or expose field-level provenance. Lifecycle is
implicit in `ToolExposureAuthority`, not present as a first-class route field.

## Taxonomies and public dependencies

- Task classes: inspection, mutation, verification, explanation, planning,
  blocked.
- Specialists: general, repository inspector, implementation, verification,
  debugging, documentation, security review.
- Immediate families: 13 `ToolFamily` values spanning discovery, inspection,
  execution, proposals, mutation, terminal response, clarification, and block.
- Response modes: action, final answer, clarification, blocked.
- Risk: low, medium, high, critical.
- Lifecycle phases: inspection, proposal, mutation, verification, answer.
- Reason codes: 36 flat enum values.

`Agent`, `Planner`, `ToolExposureAuthority`, evaluation code, and public tests
depend on `RoutingDecision`. The v0.10 `RouteDecision` projection also supplies
older specialist names such as `python_verification` and
`verilog_verification`.

## Reliability gaps

- A single ordered semantic rule path determines too many independent fields.
- Specialist/family candidates are not represented by an explicit
  compatibility matrix.
- Tool sets are attached to semantic branches and only later filtered, rather
  than being constructed as a documented intersection.
- Reason code selection is coupled to phrase branches and overlaps family,
  lifecycle, and task semantics.
- Risk and capability requirements are deterministic, but their rules are not
  represented as typed hard constraints with effects and override policies.
- Confidence does not cause abstention or safe fallback.
- Plausible repository-discovery defaults can hide semantic uncertainty.
- There is no complete per-field decision trace or final cross-field solver.
- The flat 36-code reason taxonomy and unrestricted branch competition are
  large/ambiguous targets for a local 7B model.

## v0.11.1 integration constraint

The smallest safe integration is a versioned staged router that preserves the
existing enums and adapts its final result into `RoutingDecision`. Existing
tool exposure and registry checks remain authoritative. The legacy router
remains selectable until live development and untouched-holdout gates pass.

## Blind-data boundary

No individual file, prompt, label, case identifier, output, or explanation from
`evaluation_results/v0.11.0-rc3-1/` was inspected. Its content was streamed only
to a single aggregate SHA-256 before implementation so the directory can be
verified unchanged afterward. New development assets must reject this path and
related sealed/private-label references.
